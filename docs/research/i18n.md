## 1. Summary

**Question.** The web UI is English only and `web/` has no translation framework (ROADMAP,
*Translations (i18n)*). What should Dupearr use: a library, or a small helper of its own? How big is
the job of extracting the strings, and which texts does the Go server write in English that the UI
shows as they are? And how do we keep translated text that decides whether someone removes a file
(dry run, permanent deletion, approval, recycle bin) accurate?

**Answer.**

* **Size.** `web/src` holds about **2,600 user-visible string occurrences, about 2,030 unique
  strings and about 11,400 words** in 166 non-test files (MEASURED, §2.2). About 10–15 % of them
  are not text to translate: codec, HDR and service names, date-format tokens, and month or
  language names that `Intl` already provides. The largest areas are the settings pages (profile
  explanations, Media Management, General), the duplicate pages (comparison, approval dialogs) and
  the label maps in `lib/constants.ts` (281).
* **Structure is the harder part.** 123 JSX elements mix text with values or elements, and 76 of
  them put `<strong>`, `<code>`, `<Link>` or `<ByteSize>` inside a sentence. Some sentences are
  assembled from English fragments (the profile explanation, "One copy to remove is … hardlinked").
  There are about 35 English-only plural ternaries (`n === 1 ? … : …`) and two local `plural()`
  helpers. Validators return English strings. Extracting one key per literal would give translators
  fragments they cannot translate. Most of the work is rewriting these into whole messages with plural and
  rich-text support (§2.3–2.4).
* **Formatting.** `lib/format.ts` hard-codes `en-US`/`en`, formats decimals with `toFixed`, and has
  English month and weekday names and English compact durations. `Intl` covers all of these.
  `Intl.DurationFormat` even reproduces today's English "2h 13m" exactly (MEASURED), but it needs
  Chrome 129 / Firefox 136, above Dupearr's minimum of Chrome 111 / Firefox 128, so it needs a
  fallback (§2.5, §3.8).
* **Server texts are English, and most are stored.** The Go code builds these in English and keeps
  them in SQLite: group status reasons, the "decided by" explanation lines, protection reasons and
  the comparison values. Health-check messages, API error and validation messages, history titles
  and messages, notification field labels and notification messages are English too. The UI cannot
  translate free text. It *can* translate the codes that travel with it (status, flags, deciding
  criterion, event type, health source, `permanent`). Translating the rest needs message codes with
  arguments from the server (Phase 4, §5.6), not a server-side UI language (§2.6).
* **Library.** **react-intl (FormatJS)** fits best:
  * ICU MessageFormat (plural, select, rich text);
  * per-message fallback to an English `defaultMessage` held in the code;
  * no build plugin, and no `eval` (CSP-safe);
  * six runtime packages, BSD-3-Clause/MIT, about 15 kB gzip, very active;
  * Weblate has a native "Format.JS JSON" format with translator descriptions and an ICU check.

  The alternatives each have a drawback:
  * **i18next** works, but its default syntax is not ICU, and its ICU plugin requires
    `intl-messageformat` below 12.
  * **Lingui** needs a Babel or SWC macro step in a build that runs on Oxc. It declares about 35
    runtime packages and shows hashed ids for messages that were not compiled.
  * **typesafe-i18n** has had almost no maintenance since its creator died in 2023, and it uses its
    own syntax.
  * **Paraglide** advises against lazy-loading translations, Weblate support for its default
    inlang message format is UNVERIFIED, and a small team maintains it. Its documented setup loads
    format plugins from a CDN, but local module paths are also supported, so that is a
    configuration matter, not a blocker.
  * **A helper of our own** on `Intl` is small, but it would have to reimplement ICU plurals, select
    and rich text. Safety-critical sentences are the wrong place to save 15 kB (§3).
* **Platform.** Hosted Weblate's Libre plan fits. It is free for public libre projects, with the
  limits of its 160k plan, and Weblate itself is GPL. It is the same kind of workflow Sonarr and
  Radarr use. "Enable reviews" and the commit filter "Only include approved translations" are
  **project** settings, so the safety messages need a Weblate project of their own (or one
  project that is approved-only for everything). The committed JSON files carry no approval
  state: CI can check that a translation is present and matches English, not that it was
  approved. Approval is enforced by the Weblate configuration and a release checklist. Crowdin's
  open-source licence requires contributing the translations to Crowdin's Global TM (§3.11).
* **Safety.** A translation can mislead in several ways:
  * a dry run described as a deletion, or the reverse;
  * "would be permanent" turned into "permanent";
  * a dropped or swapped number;
  * a stale translation after the English wording changed its meaning;
  * a mistranslated setting (the direction of a criterion, "keep per", the per-file override) that
    makes a profile keep the worse copy, which auto mode then acts on without another look.

  The design (§4, §5.3):
  * Safety messages get their own id prefix and their own catalogue files. They include the
    controls and explanations that decide which copy is kept.
  * The English text of a safety message cannot change under its id, and a retired id is never
    reused: a lock file with tombstones and a test enforce it.
  * Translations of safety messages come only through a Weblate project with reviews on that
    commits approved strings only.
  * Every translation is checked against English for arguments, tags and plural categories.
  * A safety message that is missing, stale or broken falls back to English, message by message.
    Other messages fall back when missing or broken; a stale `ui` translation is a known,
    bounded limitation (§5.1).
  * The typed confirmation word is never translated.
  * Numbers are always formatted for the active locale.
  * The signals that do not depend on text (danger button, badge colours) stay as they are. At
    badge level they do not tell a dry run from a real removal (only the row or event does), so
    hypothetical badges get a visual marker of their own.
  * A language is offered only when every safety message is translated (checked in CI) and
    approved (checked in Weblate by the release checklist).
  * Before server texts are translated (Phase 4), the server's own gates must stop matching its
    English status reasons (§2.6, S16).

**Recommendation: build a first slice**, after the dependency discussion that CONTRIBUTING asks for
(`CONTRIBUTING.md:47–49`). Phase 1 includes:

* `react-intl` as the only new runtime dependency (the tests also declare its parser,
  `@formatjs/icu-messageformat-parser`, which is already in its tree, §6.4);
* the provider and locale settings, and formatters that follow the locale;
* a catalogue generated by a Vitest script (no extraction tool);
* the catalogue, parity and safety tests, and a pseudo-locale for tests;
* the app shell and the safety-critical messages (≈600 occurrences, including the label maps),
  plus the labels of the controls that decide which copy is kept (§4.1 g).

Phase 1 ships **no new language**. It makes each page (Phase 2, except Profiles, which follows the
safety rules) and each language (Phase 3) its own good first issue, and it builds in the safety
rules from the start: those are the hardest part to add later. Server texts stay English until
Phase 4 designs message codes, which must first replace the server's matching of English status
reasons.

## 2. Today in Dupearr

### 2.1 How the UI is built, served and configured

* **Stack.** React 19, TypeScript, Vite, React Router, TanStack Query and Tailwind CSS v4
  (`docs/ARCHITECTURE.md:44`, §9 at `:427`). The Vite major is 8 (`web/package.json:40`), which
  bundles with Rolldown. There are six runtime dependencies
  (`web/package.json:19–26`). CONTRIBUTING: "**No new dependencies** without discussion … Web: the
  packages already in `web/package.json`" (`CONTRIBUTING.md:47–49`). CI gates on
  `npm audit --omit=dev` (`:128`), so every runtime dependency's tree is audited.
* **Chunks and caching.** 20 routes are lazy-loaded (`web/src/router.tsx:12–35`, `lazy()`), plus
  the development-only UI kit page (`:92`). Vite's hashed
  chunks under `/assets/` are served with `Cache-Control: public, max-age=31536000, immutable`
  (`internal/api/spa.go:23`, `:83`). A per-locale catalogue loaded with `import()` fits this
  (INFERRED).
* **Content-Security-Policy.** `pageCSP` (`internal/api/spa.go:147–171`) allows
  `script-src 'self'` plus the hashes of the page's own inline scripts, and
  `connect-src 'self'`. There is no `'unsafe-eval'`, so a runtime that compiles messages with
  `eval`/`new Function` would fail. A same-origin locale chunk is allowed.
* **Language attribute.** `<html lang="en">` is fixed (`web/index.html:2`). It is never updated,
  which matters for screen readers, hyphenation and CSS `text-transform: uppercase` (used 10 times).
* **Preferences.** UI preferences are stored **per browser** in `localStorage` under `dupearr.ui`
  (`web/src/app/preferences.tsx:11–34`). They cover the theme, the \*arr-style short and long date
  formats and time format, relative dates and the sidebar. The UI page says "Saved in this browser
  and applied immediately." (`web/src/pages/settings/UiPage.tsx:81`). `usePreferences()` returns the
  defaults when there is no provider (`preferences.tsx:93–104`), so tests render components without
  it. The i18n design reuses this pattern (§5.3).
* **No language negotiation.** The server has no locale concept. `Accept-Language` appears only in a
  header allow-list for notifications (`internal/notifications/headers.go:20`).

### 2.3 How the text is structured

* **Inline English** in JSX text and props makes up most of it. There is no indirection today.
* **Label maps** in `lib/constants.ts` map every API enum to a label and often a description.
  Examples are `GROUP_STATUS_DESCRIPTIONS` (`:309`), `GROUP_FLAG_DESCRIPTIONS` (`:361`),
  `ACTION_STATUS_LABELS` (`:529`), `DELETION_METHOD_DESCRIPTIONS` (`:557`),
  `HISTORY_EVENT_LABELS` (`:563`) and `MODE_LABELS` (`:693`). `labelOf` falls back to `humanize`
  for values a newer server sends (`:57–72`). The maps also hold many technical names that stay as
  they are (resolutions, HDR formats, codecs, containers, audio formats, notification services).
* **Pure helpers and validators return English strings.** Examples: `rules/validation.ts`,
  `rules/criteria.ts` (`${bad.length} pattern${…} invalid`, `:807`), `connections/hostConfigForm.ts`,
  `connections/connectionUtils.ts`, `connections/notificationForm.ts` and
  `rules/mediaManagement.ts` (`recycleBinProblems`, `:254`). They run outside React.
* **Sentences assembled from fragments.**
  * The direction wording of numeric criteria has phrases such as
    `higherPhrase: 'the higher custom format score'` (`rules/criteria.ts:178–225`).
    `explainCriteriaParts` (`:566`), `explainKeep` (`:617`) and `describeProtection` (`:632`) splice
    them into English sentences. `ProfileExplanation.tsx` then joins the clauses with `"; "` and
    `"."`.
  * `DecisionSummary.tsx:41–42` builds "One copy to remove is / N copies to remove are hardlinked —
    removing it/them won't free space".
  * `ApproveGroupDialog.tsx` renders "Remove **n** of m copies, reclaiming **size**." across four
    JSX nodes.
  * `BulkActionDialog.tsx:155–162` builds "Approve **N files** from **M groups**, reclaiming …".
* **Mixed JSX.** 123 JSX elements mix text with expressions or child elements. 76 of them contain
  inline elements (`<strong>`, `<code>`, `<Link>`, `<ByteSize>`) (MEASURED). Each needs one message
  with rich-text tags, not several keys.
* **Toasts.** 73 titles. Their messages are mostly template literals.
* **Typed confirmation.** `TYPED_CONFIRM_WORD = 'DELETE'` (`duplicates/duplicateUtils.ts:116`) is
  compared at `BulkActionDialog.tsx:97` and shown in the instruction "Type **DELETE** to approve N
  groups:" (`:282–283`).
* **Language names.** `COMMON_LANGUAGES` (`rules/criteria.ts:375`, 27 entries) holds English names
  of ISO 639-2 codes.
* **Labels from the server.** Notification provider fields show the server's `label` and
  `helpText` as they are (`connections/SchemaFields.tsx:64`, `:175`). Criterion labels prefer the
  server schema's `label` (`rules/criteria.ts:82–84`).

### 2.4 Plurals and interpolation

* **Plurals.** There are 38 ternaries on `=== 1` / `!== 1` in non-test code (MEASURED); about 35
  of them choose singular or plural text, for example
  `{protections} protection{protections === 1 ? '' : 's'}` (`ProfileCards.tsx:62`),
  `${days} day${days === 1 ? '' : 's'}` (`TasksTables.tsx:51`, `mediaManagement.ts:16–17`) and
  `formatFileCount` (`lib/format.ts:369–373`). Two local helpers,
  ``plural(n, one, many = `${one}s`)`` (`BulkActionDialog.tsx:50`, `DuplicatesPage.tsx:117`), have
  17 call sites on 16 lines. Verb and pronoun agreement uses more ternaries: "is/are", "needs/need", "removes/remove"
  and "it/them" (`BulkActionDialog.tsx:224–245`). Some sentences carry **two counts**, for example
  "Approve N files from M groups".
* **CLDR plural rules differ** (MEASURED with `Intl.PluralRules`, Node 24.6, ICU 77.1, CLDR 47):
  * English has `one`/`other`.
  * French maps **0 to `one`** and has `many` for 1,000,000.
  * Polish has `one`/`few`/`many`/`other`: 2 → `few`, 5 → `many`, 22 → `few`, 1.5 → `other`.
  * Arabic has all six categories.

  So no `n === 1` rule is correct outside English-like languages.
* **Interpolation.** 249 prose template literals. They interpolate counts, names, titles, paths,
  byte sizes, dates and the output of other helpers.

**Conclusion.** All of this is English only. Most of the group texts are persisted as English
sentences, so no client-side change can translate existing rows. The UI can already translate the
structured codes next to them. It should keep showing the English sentence as the detail, marked
`lang="en"`. A later server change (§5.6) can add message codes with arguments to the API. The API
contract allows additive fields (`docs/CONTRACTS.md`, CONTRIBUTING: "additions are fine").

**Server logic reads some of this English (CODE).** Two safety gates match the exact English of
a stored status reason:

* The scanner sends a group to review with the reason `incompletePrefix + …`, where
  `incompletePrefix = "Incomplete data: "` (`internal/scanner/persist.go:22`, `:94`). When an
  \*arr instance could not be read, the reason also contains `arrUnreadableReason =
  "(keep tags, tracked files and the download queue may be missing)"`
  (`internal/scanner/enrich.go:379`, added at `persist.go:497`).
* `ArrDataMissing` recognises such a group by `strings.HasPrefix(g.StatusReason,
  incompletePrefix) && strings.Contains(g.StatusReason, arrUnreadableReason)`
  (`enrich.go:385–387`). Manual approval is refused on it (`internal/api/duplicates.go:343–348`),
  because files the unreadable instance tracks look untracked (a keep tag may be missing).
* Re-evaluation keeps incomplete-data groups in review by the same prefix
  (`internal/scanner/maintenance.go:280`), and `unavailable.go:130` keeps their reason.
* `internal/executor/executor.go:368` compares the stored `StatusReason` before and after
  approval. A changed text there refuses the action, which is the safe direction.

So rewording these strings, or rendering them from codes with a slightly different English,
would silently disable the approval block for groups whose \*arr data is missing. The web UI does
not match server text to decide anything; two helpers compare field labels with server
validation messages for display only (`connections/connectionUtils.ts:128`,
`rules/mediaManagement.ts:171`).

⇒ English must stay the default and be available **synchronously**, and components must render

### 2.8 Size baseline (MEASURED on the current `web/dist`)

* JavaScript: 860 kB raw, ≈ 292 kB gzip (sum over the chunks). Of that, `vendor-react` is 348 kB
  raw, 107 kB gzip, and application code is 512 kB raw. CSS: 55 kB raw, 10 kB gzip.
* The unique English text is ≈ 70 kB raw, ≈ 23 kB gzip. A locale file with keys would be about
  70–100 kB raw, loaded only by users of that language (INFERRED). The Go binary embeds `web/dist`,

### 2.9 Gaps

1. There is no message indirection, no locale setting, and `lang` is fixed.
2. Sentences are built from fragments, and there are English-only plurals and verb agreement.
3. Formatting is hard-coded to English, including the decimal separator.
4. Server texts are English and persisted, with codes only partly present, and two server gates
   match the English of a status reason.
5. There is no rule for translated safety text: who may change it, how staleness is detected,
   what happens when it is missing.

### 3.2 Message syntax

* **ICU MessageFormat (v1)** is the common format:
  * FormatJS uses it natively `[FJS]`.
  * Lingui compiles it `[LIN]`.
  * Paraglide's default plugin uses it (`{count, plural, one {# item} other {# items}}`,
    `[PG] docs/file-formats.md`).
  * Weblate has an "ICU MessageFormat" check (flag `icu-message-format`) for "Syntax errors and/or
    placeholder mismatches". The check is enabled automatically for the Format.JS JSON and ARB
    formats `[WL checks]`.

  A catalogue in ICU therefore works across runtimes: if the runtime ever changes, the translations
  survive. That is the exit strategy.
* **i18next** uses `{{name}}` interpolation and CLDR suffix keys (`_zero`, `_one`, `_two`, `_few`,
  `_many`, `_other`, JSON v4). Its plurals "are streamlined with the one used in the Intl API" and
  need `Intl.PluralRules` `[I18N plurals]`. Weblate supports "i18next JSON file v4". It "stores
  plurals using standard CLDR suffixes" and offers a per-category plural editor
  (`[WL] docs/formats/i18next.rst`).
* **MessageFormat 2** (`Intl.MessageFormat`) is at **Stage 1** `[TC39]`. It is not usable in
  browsers today.

### 3.3 react-intl / FormatJS

* **Versions and licences.** `react-intl` 12.1.3 (BSD-3-Clause). It depends on `@formatjs/intl`
  (MIT), `intl-messageformat` (BSD-3-Clause), `@formatjs/icu-messageformat-parser` (MIT),
  `@formatjs/icu-skeleton-parser` (MIT) and `@formatjs/fast-memoize` (MIT). That is **6 packages**,
  all from FormatJS `[NPM]` (tree resolved from the latest versions, INFERRED). Peer dependencies:
  `react >= 18`, `@types/react >= 18`.
* **Activity.** Published 2026-09-24; 2.28 million weekly downloads (`intl-messageformat`: 13.9
  million); repository pushed on 2026-09-24 `[NPM]`.
* **Size.** 51.1 kB minified, **15 kB gzip** for `IntlProvider`, `useIntl` and `FormattedMessage`.
  `intl-messageformat` alone is 33.5 kB / 9.9 kB `[BJS]`. Messages precompiled to an AST let the
  parser be aliased away ("~40% less") `[FJS guides/advanced-usage.mdx]`. That needs a compile step,
  so it is not part of the first slice.
* **Fallback.** The documented message fallback is `[FJS react-intl/api.mdx:470–480]`:
  1. format the translated message at `id`;
  2. format the `defaultMessage`;
  3. use the translated message's source unformatted;
  4. use the `defaultMessage` source;
  5. use the literal `id`.

  `defaultLocale` should be the language of the `defaultMessage`s, "so that a sentence is coherent
  in a single locale" (`api.mdx:156`). **Consequence for Dupearr (PROPOSED):** every call must
  carry the English `defaultMessage`. A missing or broken translation then renders formatted English
  (step 2), never a raw template (step 3) or the id (step 5).
* **Fallback in the code** (CODE, `@formatjs/intl` 6.1.2 `index.js`):
  * A message that is absent reports `MissingTranslationError` through `onError` only when there
    is no `defaultMessage` or the locale differs from `defaultLocale` (`:241`). English with a
    `defaultMessage` therefore reports nothing.
  * `onError` is called **before** the fallback: in the `catch` of the translated message
    (`:255–256`, the `defaultMessage` follows at `:258–260`) and before formatting the
    `defaultMessage` of an absent one (`:241`). An `onError`
    that throws therefore propagates and suppresses the English fallback.
* **Context.** `react-intl` 12.1.3 exports `IntlContext` (`index.d.ts:84`, `:246`;
  `index.js:59`, `:360`), so a hook can read the context and fall back when there is no provider
  (CODE).
* **Rich text.** Tags in messages map to functions supplied by the code. Attributes on tags are
  ignored, self-closing tags are literals, and "all tags specified must have corresponding values
  and will throw error if it's missing" `[FJS intl-messageformat.mdx:150–180]`. `IntlProvider`
  accepts `defaultRichTextElements`, a central map for tags such as `<b>`, and
  `wrapRichTextChunksInFragment` `[FJS react-intl/components.mdx]`. A translator cannot add a link
  target or an attribute (INFERRED).
* **Types.** Ids can be restricted with `declare global { namespace FormatjsIntl { interface
  Message { ids: keyof typeof messages } } }` `[FJS react-intl.mdx:268–276]`. Arguments can be typed
  per id with `FormatjsIntl.MessageArguments` `[FJS api.mdx:655–700]`.
* **Outside React.** `createIntl` and `createIntlCache` format without a provider
  `[FJS api.mdx:43–67]`.
* **Runtime needs.** `Intl.PluralRules`, `NumberFormat` and `DateTimeFormat`. `formatDuration`
  needs `Intl.DurationFormat` or a polyfill `[FJS guides/runtime-requirements.mdx; api.mdx]`.
  The same page states a narrow support policy: "We support **IE11** & **2 most recent versions
  of Edge, Chrome, Firefox & Safari**" (`runtime-requirements.mdx:4–5`). Dupearr's minimum
  (Chrome/Edge 111, Safari 16.4, Firefox 128) is far older than that, so whether
  `react-intl` 12 and `intl-messageformat` 12 run there is **UNVERIFIED**; the Phase 0 spike
  tests it (§5.2).
* **Parser entry points.** `@formatjs/icu-messageformat-parser` 3.5.20 exports `./printer.js`
  (`printAST`) and `./manipulator.js` (`isStructurallySame`) besides the parser (CODE,
  `package.json` exports, `printer.d.ts:150`, `manipulator.d.ts:173`). `react-intl` depends on it
  at the exact version 3.5.20. Dupearr code that imports it directly relies on a transitive
  dependency unless it is declared (§6.4).
* **CSP.** No `eval` or `new Function` in the sources of `react-intl`, `intl-messageformat`,
  `icu-messageformat-parser` and `intl` (CODE: grep of the 32 top-level source files at `[FJS]`).
* **Tooling** (optional). `@formatjs/cli` 6.16.32 `[FJS tooling/cli.mdx]`:
  * `extract` accepts custom function and component names and `--throws`;
  * `verify` has `--missing-keys`, `--structural-equality` and `--extra-keys`;
  * `compile` has `--ast` and `--pseudo-locale en-XA|xx-LS|…`.

  Extraction runs in Node.js. `compile` uses native Rust bindings with "no JavaScript compiler
  fallback", shipped for macOS arm64, Linux x64/arm64 (glibc) and Windows x64. "macOS x64/Intel …
  not supported". Dupearr does not need the CLI (§5.3).
* **Weblate.** Weblate reads a "Format.JS JSON file" (`{"id": {"defaultMessage": …, "description":
  …}}`), monolingual or bilingual. It supports descriptions, and the format adds the ICU check.
  It has no plural editor (the plural lives inside the ICU string), no flags in the file and no
  read-only strings (`[WL] docs/formats/formatjs.rst`, `formatjs-features.rst`).

### 3.8 A helper of our own on top of `Intl`

**What `Intl` provides** (MEASURED in Node 24.6.0, ICU 77.1, CLDR 47; browser versions from
`[BCD]`):

* `PluralRules` gives the categories of §2.4, with ordinals as well.
* `NumberFormat` handles grouping, the decimal separator, percent and compact notation.
* `RelativeTimeFormat` gives "gestern" for `de`.
* `ListFormat` gives "a, b und c".
* `DurationFormat` in `narrow` style gives "2h 13m" (`en`), "2 Std., 13 Min." (`de`),
  "2 h i 13 min" (`pl`).
* `DisplayNames` resolves the ISO 639-2/B codes Dupearr uses ("fre", "ger", "dut", "cze", "gre",
  "chi") through CLDR aliases: `de` gives "Französisch", "Deutsch", … (V8, MEASURED; Firefox and
  Safari UNVERIFIED).
* `NumberFormat` units are decimal only (`kilobyte` … `petabyte`).

**What it does not provide:**

* message syntax, so no plural or select inside a sentence;
* rich text;
* catalogue loading and fallback;
* checks.

**A helper would** offer `t(id, values)` with `{name}` interpolation, plurals through
i18next-style suffix keys resolved with `PluralRules`, and a small tag parser for rich text. We
estimate 150–300 lines plus the same test tooling as any library (INFERRED/PROPOSED).

**Its cost:**

* A bespoke parser for about 1,800 messages, the safety set included. Nested plural or select,
  escaping and two counts in one sentence all become Dupearr's problem.
* Translators would learn a subset syntax.
* Weblate could only check generic placeholders (flag `placeholders:`).

That is the wrong trade for 15 kB.

**Middle option.** `intl-messageformat` alone (4 packages, 9.9 kB gzip) plus about 100 lines of
React code (context, hook, rich-text rendering). It is a viable fallback if the maintainers want the
smallest ICU runtime. It gives up react-intl's tested React rich-text handling and its typing
helpers.

  *Component configuration* (`:509`). One project cannot hold an unreviewed `ui` component and an
  approved-only `safety` component. Either both are approved-only, or both commit unreviewed
  text. Components "linked to a repository in another project follow their own project's commit
  policy" (`:352–353`).
* **Per-language opt-outs.** "The approved-only policy applies only to translations with reviews
  enabled. Languages with reviews disabled through workflow customization commit all
  translations" (`:347–349`). Workflow customisation exists per project-language and **site-wide**
  per language, and the first existing setting applies (`workflows.rst:15–36`). On Hosted Weblate a
  site-wide language setting is not under Dupearr's control; whether any exists is UNVERIFIED.
  "Enabling reviews alone does not keep unapproved translations out of commits"
  (`workflows.rst:419`).
* **No approval state in the files.** Format.JS JSON "Supports flags: No", and a translation entry
  is a plain string (`formatjs-features.rst`). The committed files cannot tell an approved
  translation from one that is merely present. CI can check presence and parity with English;
  approval can only be enforced by the Weblate configuration and checked through Weblate. The
  documented project API returns `translation_review` (`api.rst:1060`), and the statistics
  endpoints return `approved` and `approved_percent` (`api.rst:3620–3623`). The commit policy and
  the per-language overrides are not in the documented project response.
* **Changed source strings.** Weblate has a state "Needs rewriting": "Translation needs to be
  rewritten because of a source string change" (`workflows.rst:163–164`). The commit policy "Skip
  translations marked as needing editing" leaves out "needs editing", "needs rewriting" and "needs
  checking" (`admin/projects.rst:341–342`). What Weblate then writes for a translation that was
  already committed is UNVERIFIED (Weblate trial).
* **Obsolete keys.** Format.JS JSON does not support "removing obsolete strings"
  (`formatjs-features.rst`), a feature for formats that store obsolete entries
  (`formats.rst:197–203`). Separately, the add-on "Cleanup translation files"
  (`weblate.cleanup.generic`) updates translation files "to match the monolingual base file. For
  most file formats, this means removing stale translation keys" (`addons-autogenerated.rst:469–480`).
  Whether it works for Format.JS JSON is UNVERIFIED.
* **Tags in the ICU check.** The ICU MessageFormat check validates simple XML tags only with
  `icu-flags:xml` or `icu-flags:strict-xml` (`checks-autogenerated.rst:775–790`). Without the flag,
  a dropped or renamed `<b>` tag is presumably not reported in Weblate (INFERRED).

### 3.12 How Sonarr and Radarr translate their UI

* **Catalogues.** The dictionaries live in the backend repository as
  `src/NzbDrone.Core/Localization/Core/<culture>.json`: 45 files at `[S4]` and 45 at `[R]`. Sonarr's
  `en.json` has 2,154 keys (MEASURED).
* **One source for UI and backend.** `GET /api/v3/localization` returns the merged dictionary
  (`[S4] src/Sonarr.Api.V3/Localization/LocalizationController.cs:23–28`). `LocalizationService`
  loads `en.json` first, then the language's base file, then the regional file, so every key falls
  back to English (`[S4] src/NzbDrone.Core/Localization/LocalizationService.cs:134–158`). The
  backend uses the same service for its own texts: `en.json` has 60 `…HealthCheckMessage` keys.
* **Frontend.** `translate(key, tokens)` returns `translations[key] || key` (so a missing key shows
  the key) and replaces `{token}` with a regular expression. It injects `appName`
  (`[S4] frontend/src/Utilities/String/translate.ts:26–43`). Radarr is the same, plus positional
  tokens for older strings (`[R] frontend/src/Utilities/String/translate.ts:26–48`).
* **No plural engine.** Strings like `"CountCustomFormatsSelected": "{count} custom formats(s)
  selected"`, or separate keys `CountSelectedFile` / `CountSelectedFiles` (MEASURED in `en.json`).
* **Language setting.** It is **server-wide**: `UILanguage`, default English
  (`[S4] src/NzbDrone.Core/Configuration/ConfigService.cs:342–346`). The UI warns that a browser
  reload is required (`[S4] frontend/src/Settings/UI/UISettings.js:212–227`).
* **Process** (`[SW] sonarr/contributing.md`, "Translation"). A "self hosted open access Weblate
  instance" (translate.servarr.com) manages the files. "The English translation, `en.json`, serves
  as the source … and is managed on GitHub repo". "Editing of translated strings … should be
  performed" on Weblate. And: "**PRs for translation of log messages will not be accepted**".

**Lessons for Dupearr:**

* Adopt: per-key English fallback, a single English source managed in the repository, Weblate,
  and English logs.
* Avoid: showing keys when a message is missing, and "(s)" plurals.
* Reconsider: the server-wide language setting. Dupearr's other UI preferences are per browser, and
  Dupearr's server texts are persisted English, so server-side translation would not reach them
  (§2.6).

## 4. Safety analysis: correctness of safety-critical text

For Phases 1–3 the risk is not a removal decided by code from translated text: the server never
reads UI text. The risk is a **person** deciding wrongly because a translated text told them
something false. That includes a person *configuring* a profile wrongly, which auto mode then acts
on without another look (S15). The server does read its own English status reasons in two safety
gates (§2.6), so Phase 4, which touches server texts, can cause a wrong removal through code (S16).

The guiding rule for safety messages mirrors Dupearr's handling of unknown data: **a safety
translation whose state is unknown (missing, stale, unreviewed or broken) is treated as no
translation, and the English text is shown.** A translation is never assumed to be correct. For
`ui` messages the design guarantees the fallback for missing and broken translations only (§5.1).

### 4.1 What counts as safety-critical (PROPOSED definition and inventory)

A message is safety-critical when it tells the user one of these things:

* (a) whether files **will be, were, or would have been** removed (dry run against a real run);
* (b) whether a removal is **permanent or recoverable** (recycle bin);
* (c) what an **approval or confirmation** does: how many files, which copies, which method;
* (d) why a copy is **kept, protected, deferred or in review**;
* (e) what **restoring a backup, cancelling or restoring a file** does;
* (f) what a **setting that changes what is removed** does: mode, circuit breakers, minimum age,
  recycle-bin path and clean-up, deletion methods, disc removal, exclusions, protections;
* (g) **which copy is kept**: the controls and explanations of a profile and of the per-file
  override. A swapped or ambiguous translation here makes a user save a profile that ranks the
  worse copy first (S15).

### 4.3 Review rules for safety messages (PROPOSED, for CONTRIBUTING)

1. **Mark them.** Ids start with `safety.`. Each message has a description that starts
   "SAFETY:" and says what must survive translation: the numbers, the hypothetical mood of dry
   runs, permanence against recycle bin, negations.
   The controls and explanations that decide which copy is kept (§4.1 g) are safety messages too.
   Safety messages live in their own catalogue files (`safety.<locale>.json`), and the safety
   components use only `safety.*` messages (a test checks it, §6.2).
2. **English is immutable per id, and ids are never reused** (S2). Fix a typo by adding a new id.
   Retiring an id is allowed: its lock entry becomes a tombstone.
3. **Translation only through the Weblate safety project.** Because the commit policy and "Enable
   reviews" are **project** settings (§3.11), the safety messages get a Weblate project of their
   own. Its project settings: reviews on, translation quality filter "Only include approved
   translations". Its component: the enforced checks include ICU MessageFormat, the flags are
   `icu-message-format, icu-flags:strict-xml`, and there is no automatic translation. No
   per-language workflow customisation may turn reviews off, because that language would then
   commit everything. Translations should be made on Weblate, as in Servarr, where editing
   translated strings "should be performed" on Weblate (`[SW] sonarr/contributing.md:152`). For
   safety files the rule is strict: changes to `safety.<locale>.json` come only from Weblate's pull
   requests, and CODEOWNERS on those files and on `safety-lock.json` requires a maintainer's
   review. The one exception is a maintainer PR that only **removes** keys (obsolete or retired
   ids, §5.3). Whether Weblate stops a reviewer from approving their own suggestion is UNVERIFIED;
   the rule is that a second person approves.
   **Approval cannot be checked in CI:** the committed files carry no approval state (§3.11).
   CI checks presence, parity and the lock. Approval rests on the Weblate configuration, which the
   release checklist verifies (§5.5).
4. **Glossary.** Each language fixes translations for *remove*, *delete*, *permanent*, *recycle
   bin*, *dry run*, *approve*, *keep*, *protected*, *ignore*, *queue*, *restore* and *exclusion*,
   and for the profile controls *newer*/*older*, *larger*/*smaller*, *higher*/*lower*, *more*/*fewer*
   and *best first*. The translations stay distinct wherever English distinguishes the terms.
5. **A named reviewer per language** is listed in the i18n README. Without a reviewer, a language
   is not released.
6. **English is the reference.** Bug reports quote English. Settings → UI allows switching to
   English at any time.

## 5. Proposed design

### 5.1 Decision (PROPOSED entry for `docs/DECISIONS.md`, "Translations (issue #10)"; the maintainers assign the number)

* **Runtime.** The web UI uses **react-intl** (FormatJS) with **ICU MessageFormat** messages. It is
  the only new runtime dependency. There is no build plugin and no extraction tool.
* **Messages.**
  * They are declared with `defineMessages` in co-located `messages.ts` modules.
  * Each has an **explicit, stable id** (`area.component.purpose`), the **English text as
    `defaultMessage`** and, where it helps, a `description`.
  * Ids of safety messages start with `safety.` (§4.3); all other messages are called `ui`
    messages in this document.
  * Components reference the declared objects, never string ids. A reference to a message that
    does not exist is a TypeScript error.
* **English is the source and the fallback.** It is always present in the code. Other locales are
  lazily loaded JSON chunks. Any message that is missing, empty or fails to format renders in
  English. A **safety** message whose English changed also renders in English, because the lock
  forces a new id. A **`ui`** message whose English changed under the same id keeps its old
  translation until Weblate marks it "Needs rewriting" and a translator updates it (§3.11): the
  design detects nothing there. Mitigations: the author rule that a change of meaning gets a new id
  (all messages), and a CI step that lists the `ui` ids whose English changed against the merge
  base, so the reviewer decides. That limitation is accepted for `ui` messages only because
  everything that decides a removal is a safety message (§4.1).
* **Locale preference.** Per browser (`dupearr.ui.locale`: `"auto"` or a locale code). `"auto"`
  matches the browser's languages against the **released** locales only; the default is English.
* **Server texts stay English**, and so do logs, history records and notifications. The UI
  translates the codes that travel with them. A later change adds message codes with arguments.
* **Safety messages** follow §4.3. Weblate (Libre plan) hosts **two projects**: a UI project
  (commit policy "Skip translations marked as needing editing") and a safety project (reviews on,
  "Only include approved translations"). If the Libre plan allows only one project (UNVERIFIED),
  the fallback is one project that is approved-only for everything, which slows the `ui`
  translations but is equally safe.
* **RTL is out of scope** for now.

### 5.3 Phase 1 (first slice): framework, formatters, tests, shell and safety set

**Dependency.** Add `react-intl` (runtime). The tests declare `@formatjs/icu-messageformat-parser`
as a development dependency at the version `react-intl` pins; it is already in the production tree
through `react-intl` (§6.4).

**Files** (PROPOSED):


**Loader.** For a locale, `locales.ts` loads `<locale>.json` and `safety.<locale>.json` with two
`import()` calls and merges them. It drops any `safety.*` key found in the `ui` file, so a safety
text can never arrive through the unreviewed path, and it drops empty strings. Keys that are
retired, tombstoned or absent from English are rejected by the catalogue tests in CI (§6.1), and
the code never requests them, because it references only live descriptors; the loader does not
need the lock file at runtime.

**Declaring and using messages.** An example for the approval summary, written as one ICU message
instead of four JSX fragments:

```ts
// components/duplicates/messages.ts
export const approveMessages = defineMessages({
  summary: {
    id: 'safety.approve.summary',
    defaultMessage:
      'Remove <b>{removals, number}</b> of {total, plural, one {# copy} other {# copies}}, reclaiming <b>{size}</b>.',

// ApproveGroupDialog.tsx
<T message={approveMessages.summary} values={{ removals: removals.length, total: files.length, size: fmt.bytes(bytes) }} />
```

* **Label maps** become `Record<Enum, MessageDescriptor>`, for example
  `GROUP_STATUS_MESSAGES: Record<GroupStatus, …>`. TypeScript keeps them exhaustive; unknown values
  still fall back to `humanize`. Technical names stay plain strings on purpose: resolution, HDR,
  codec, container and audio-format labels, and service names. A comment lists them.
* **Validators** return `{ message, values }` descriptors instead of strings, and the component
  formats them. Phase 1 converts `recycleBinProblems`; the others follow in Phase 2.
* **Rich text.** Dupearr's default tags `<b>`, `<code>` and `<em>` map to its styles.
  Component-specific tags (`<link>`, `<size>`) are passed per call. A tag without a value is an
  error, so the message falls back to English (S5).

**Locale.**

* Add `locale: 'auto' | LocaleCode` to `UiPreferences` (`preferences.tsx:11`), default `'auto'`.
* `I18nProvider` resolves the locale: an exact tag, then the language subtag, against
  `RELEASED_LOCALES`, else `en`. It sets `document.documentElement.lang`.
* `I18nProvider` sits in `App.tsx` next to `PreferencesProvider`, above `ToastProvider` and the
  router. The `/login` and `/setup` routes are outside `AuthGate` (`router.tsx:37–38`), and toasts
  are rendered above the router, so a provider inside `AuthGate` would miss both. The provider
  handles the loading state itself: English renders at once, and the page switches when the chunk
  arrives (or it waits briefly behind the existing `LoadingIndicator`; to decide in the spike). On
  failure it keeps English and shows a notice (S12).

  text says that server messages, history and logs stay in English. The select is hidden while only
  English is released; development builds show the pseudo-locale.

**Formatting** (`lib/format.ts`).

* Each helper gets an optional `locale` parameter, default `'en'`, so today's output and tests stay
  unchanged. `useFormat()` binds the active locale. `ByteSize` and `RelativeTime` use it in Phase 1,
  so sizes and dates follow the locale everywhere.
* Numbers use `Intl.NumberFormat` with fixed fraction digits instead of `toFixed`.
* Binary unit symbols ("{value} GiB") and "just now" / "Disabled" become messages.
* Durations use `Intl.DurationFormat` (`narrow`) when it exists, otherwise a message-based
  fallback. The `DurationFormat` path gives today's English strings exactly (MEASURED, §9). The
  fallback does not exist yet; that it gives the same English is PROPOSED and needs a test (§6.2).
* Month, weekday and day-period names come from `Intl.DateTimeFormat`. The \*arr token formats are
  kept. A new "locale default" option uses `dateStyle: 'medium'` (PROPOSED).
* `COMMON_LANGUAGES` names come from `Intl.DisplayNames`, falling back to the code.

### 5.5 Phase 3: Weblate and languages

* **Weblate projects.** Apply for Hosted Weblate Libre. The commit policy is a project setting
  (§3.11), so there are two projects:
  * **UI project**, one component (Format.JS JSON, source `web/src/i18n/catalog/en.json`,
    translations `catalog/<locale>.json`). Commit policy "Skip translations marked as needing
    editing".
  * **Safety project**, one component (source `catalog/safety.en.json`, translations
    `catalog/safety.<locale>.json`). Reviews on, translation quality filter "Only include approved
    translations", no per-language workflow customisation that turns reviews off (and an explicit
    project-language setting with reviews on, should Hosted Weblate have a site-wide override),
    ICU check enforced, no automatic translation.

  Both components carry the flags `icu-message-format, icu-flags:strict-xml` so that the ICU check
  covers tags. Set the translation licence to GPL-3.0-or-later, add the glossary, install the
  "Cleanup translation files" add-on if the trial shows it works for Format.JS JSON, and turn on
  pull requests to the public repository. If the Libre plan allows only one project, use one
  project that is approved-only for everything (§5.1).
* **Each language is its own issue:** a translator, a reviewer, then the release.
* **Release gate** (PROPOSED numbers):
  * 100 % of the safety messages translated and approved;
  * at least 90 % of all messages translated;
  * the catalogue tests pass;
  * a named reviewer.
* **What checks the gate.** The committed files cannot show approval (§3.11), so the gate has two
  parts:
  * **CI (release workflow).** A test asserts that `safety.<locale>.json` of every entry of
    `RELEASED_LOCALES` holds every live safety id, that parity passes, and that the overall share
    is met. With the approved-only policy, presence means approval **only if** Weblate is
    configured as above.
  * **Release checklist (a maintainer, before each release).** Query the Weblate API: the safety
    project has `translation_review: true` (`[WL] api.rst:1060`), and the statistics of each
    released safety translation show `approved_percent` 100 (`api.rst:2748`, `:3620–3623`). Check
    in the Weblate UI that the commit policy is still approved-only and that no language opts out
    of reviews; the documented project API does not return these (UNVERIFIED whether another
    endpoint does). CODEOWNERS on `web/src/i18n/catalog/safety.*.json` and `safety-lock.json`, and
    the rule that changes to safety locale files come only from Weblate's pull requests (§4.3),
    complete the process.
* **New safety messages after a release.** A PR that adds a `safety.*` id does not fail on `main`
  because released locales lack it: the gate test runs in the release workflow (on release tags or
  branches), not on every PR. On `main` the new message renders in English in every language (a
  whole message, so the sentence itself is never mixed, S6), and a CI note lists the missing
  translations per released locale. Before a release, either the translations are approved or the
  locale is removed from `RELEASED_LOCALES` for that release.

Once a locale other than English is released, the Language select appears.

### 5.6 Phase 4 (later, needs its own design): message codes from the server

Add optional, additive API fields so the UI can translate server texts. The English sentence stays
as the fallback and for the audit trail:

* `HealthCheck.messageKey` and `args`, next to `source`;
* `DuplicateGroup.statusReasonCodes` (`[{code, args}]`);
* `GroupFile.reasonCodes` (the "decided by" lines as `{code, args}`) and `protectedReasonCodes`;
* `ValidationFailure.code` and `args`.

**Prerequisite (safety, S16).** Server logic depends today on the exact English of status reasons
(§2.6): `ArrDataMissing` (`internal/scanner/enrich.go:385–387`), which blocks approval
(`internal/api/duplicates.go:343–348`), and the review retention of incomplete-data groups
(`maintenance.go:280`, `unavailable.go:130`). These reasons are built in the scanner
(`persist.go:94`, `:497`), not in the engine builders below. Before any status reason is reworded
or rendered from codes, Phase 4 must:

1. replace the prefix and substring matching with a structured field stored with the group (for
   example a status-reason code, or a flag such as "\*arr data missing");
2. migrate stored rows, deriving the field from today's exact English, so rows written before the
   change keep the approval block;
3. keep the existing gate tests (`internal/api/review_test.go:430`,
   `internal/scanner/safety_test.go:103`, `followup_test.go:203`) passing on rows written before
   and after the change.

Until then, Go tests freeze the exact text of `incompletePrefix` and `arrUnreadableReason`. The
comparison in `internal/executor/executor.go:368` refuses an action when the reason changed, which
is the safe direction, but it too should compare the structured field once it exists.

The engine's text builders (`evaluate.go:665–768`, `:929`) and the scanner's reason builders would
then produce codes first and English from them. Stored rows keep their English text, and new scans
add codes. Notifications stay English, or a later server-wide "notification language" setting could
change that. Server-side translation of free text is not planned.

## 6. Test strategy

### 6.1 Catalogue tests (Vitest, `web/src/i18n/*.test.ts`)

1. **Generation.** The committed `en.json` and `safety.en.json` equal the catalogue built from all
   `messages.ts` modules. Ids are unique, and a duplicate id with different text fails. `en.json`
   holds no `safety.*` id, and `safety.en.json` holds only `safety.*` ids.
2. **Syntax.** Every message in every locale parses with `intl-messageformat` (`getAst()`).
3. **Parity with English.** The same argument names and types (`number`, `plural`, `select`,
   `date`) and the same tag names (`isStructurallySame` from the parser's `manipulator.js` can
   do part of this, §3.3). A locale key that is not in the English catalogue of its file fails
   (obsolete keys are removed as in §5.3). A `safety.*` key in a `ui` locale file fails.
4. **Plurals.** Every `plural` in locale L covers the categories of `Intl.PluralRules(L)`, or
   `other` plus explicit `=n` cases. Every message formats without error for sample values of each
   category (0, 1, 2, 5, 22, 1.5, 1,000,000).
5. **Safety lock.** Every `safety.*` id is in `safety-lock.json` with the SHA-256 of its English
   text. No live id matches a tombstone. No locale file holds a tombstoned id or a `safety.*` id
   missing from the lock.
6. **Typed confirmation.** The instruction message in every locale contains `{word}` exactly once.
7. **No new URLs.** A translation contains no URL, e-mail address or `@` handle that its English
   text lacks.
8. **No empty strings.** The loader drops them. The test asserts that they render English.
9. **Release gate** (§5.5) for every entry of `RELEASED_LOCALES`: presence of every live safety
   id, parity and the overall share. It runs in the release workflow, not on every PR, and it
   cannot check approval (§3.11); the release checklist does.

### 6.2 Component tests

* **Existing tests** (49 files, about 1,490 queries) keep running in English. The provider-free
  fallback of `useT` means no test needs a new wrapper. Most tests stay valid; tests of the
  sentences Phase 1 rewrites into whole ICU messages are updated with them (INFERRED, §2.7).
* **New provider tests** (with a recording `onError`, since a throwing one would suppress the
  fallback, §3.3):
  * a locale missing some keys renders English for those;
  * a broken translation (a syntax error, a missing tag value) renders formatted English, not the
    id or the template, and the recorded errors name it;
  * a `safety.*` key placed in the `ui` locale file is ignored;
  * a failed chunk load keeps English and shows the notice;
  * `lang` follows the rendered language;
  * `"auto"` ignores locales that are not released.
* **Safety components in the pseudo-locale** (`ApproveGroupDialog`, `BulkActionDialog`,
  `DryRunBanner`, `PermanentBadge`, the history removal facts, `RestoreSafetyNotes`, and for
  category (g) the criterion editors, the keep fields of `ProfileEditorModal`, `OverrideControl`
  and `ProfileExplanation`). In this test **only the `safety.*` catalogue is pseudo-translated**:
  * no visible text node lacks the pseudo markers, except an allow-list of data (titles, paths,
    sizes, proper nouns, and the built-in texts of `components/ui` primitives such as a dialog's
    close button). A text that comes from a `ui` message, or from a plain string, stays English
    and fails, so the test also proves that these components use only safety messages;
  * the button variant, the badge kinds and the hypothetical-badge marker depend on dry run and
    `permanent`, not on text;
  * the stored criterion direction and override follow the selected option's value, not its label
    (S15);
  * typed confirmation still requires `DELETE`.
* **Formatters.** `en` output is unchanged (the existing `format.test.ts` stays green). There are
  new cases for `de`, `fr` and `pl`: separators, "12 %", binary units as messages, `DurationFormat`
  and its fallback (with `Intl.DurationFormat` stubbed away), and `DisplayNames` with the fallback
  to the code.

### 6.3 Static checks (Vitest over the source tree)

* **Ratchet.** Areas marked as extracted may not gain prose literals in user-visible positions. It
  uses the scanner of §9. It needs `rolldown/parseAst`, a public export of Rolldown, which reaches
  `node_modules` through Vite. Either declare it as a development dependency or use a coarser
  regular-expression check; this is an open question (§7).
* No `dangerouslySetInnerHTML` with message output.
* No `toFixed(` or `'en-US'` in display code, with an allow-list.
* No `truncate` / `whitespace-nowrap` on the nodes that render safety messages, including the
  shared primitives they pass through: the check covers `components/ui` (`Badge.tsx:71`, `:78`
  today) and wrappers such as `ActionCells.tsx:33`, not only the safety components (S10).

### 6.4 Pseudo-locale

`pseudo.ts` transforms only the literal parts of each English message's AST. It adds accents,
brackets and about 35 % padding, and leaves arguments, plurals and tags alone. It is used in tests
and in development builds (menu entry "Pseudo"), never released. The parser exports a printer,
`printAST` from `@formatjs/icu-messageformat-parser/printer.js` (CODE, §3.3). It is a transitive
dependency of `react-intl` today, so the test code declares
`@formatjs/icu-messageformat-parser` as a development dependency at the version `react-intl`
pins (3.5.20 for `react-intl` 12.1.3). That adds no package to the production tree.
`formatjs compile --pseudo-locale` is not used, because it needs the native binding (§3.3).

### 6.5 Go, fakes and end-to-end tests

* **Phases 1–3** change no Go product code and no API. Phase 1 adds one Go test that freezes the
  exact English of `incompletePrefix` and `arrUnreadableReason` (S16), a guard that is useful
  whether or not server texts are ever translated.
* `internal/e2e` (the real binary against `internal/testutil/fakemedia`) and the fakes are
  unaffected. The fakes emulate Plex and the \*arrs, not Dupearr's text.
* **Phase 4** adds Go unit tests (every code has an English rendering, and the arguments match),
  API contract tests for the additive fields, and an e2e assertion that health and group responses
  carry codes next to the English messages. Before that, it adds the tests of S16: the exact
  English stays frozen until the structured field replaces the matching, and the approval block (`review_test.go:430`) and the review retention
  (`safety_test.go:103`, `followup_test.go:203`) pass on rows written before and after the
  migration. An e2e case can make a fake \*arr answer 503 during a scan
  (`fakemedia.Env.SetStartingUp`, `internal/testutil/fakemedia/env.go:646–655`) and assert that
  approval is refused. Whether a 503 leads to the incomplete-data reason in the scanner is
  INFERRED and would be confirmed by the test itself.

## 7. Open questions and how to help

1. **Library.** Is react-intl (6 packages, about 15 kB) acceptable, or do the maintainers prefer
   `intl-messageformat` with our own React glue (4 packages, about 10 kB, §3.8)? Either keeps the
   ICU catalogue portable.
2. **Where the locale lives.** Per browser (proposed, like the other UI preferences), or
   server-wide like Sonarr's `UILanguage`? And should `"auto"` be the default, or English until
   someone chooses?
3. **The release gate:** 90 % overall, or 100 %? Who reviews each language?
4. **Localising the typed word** `DELETE`. The proposal keeps it English. Is that acceptable for
   users who do not read English?
5. **The static scanner:** declare `rolldown` as a development dependency, or use a regex check?
6. **Glossary:** should *remove* and *delete* stay distinct terms in English first? Today "Deleted"
   labels a successful removal that may have gone to a recycle bin (`constants.ts:529–537`).
7. **Phase 4:** which server texts matter most to non-English users? Likely the health checks,
   then the status reasons. Either way, the structured replacement for the English matching of
   S16 comes first.
8. **Weblate layout:** two projects (UI unreviewed, safety approved-only), or one project that is
   approved-only for everything? The first keeps `ui` translation fast; the second is simpler to
   audit and needs no second Libre project.
9. **Stale `ui` translations:** is the reported list of changed `ui` ids enough, or should the
   lock (with tombstones) cover every message, at the cost of losing translations on every typo
   fix?
